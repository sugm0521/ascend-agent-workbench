# 报告组织与展示

## 阅读层次

首屏是一段本期结论、少量关键成果和需关注事项；主体保留具体工作；证据编号及版本/路径放末尾。摘要不能代替明细，明细也不逐行粘贴日志。按实际材料决定篇幅，不凑固定条数或虚构完成率。

每份报告采用一个一级标题，二级标题区分内容，三级标题表示日期或具体改进。事项段落优先于长表：**做了什么 → 得到什么 → 验证到哪里 → 还差什么**。一个事项已有清楚结论就不重复堆背景。路径、长SHA、命令放证据区，正文用可读名称与证据编号引用。

## 个人工作周报

建议骨架（小节无材料时合并或直说缺口，不留下模板占位符）：

```markdown
# 个人工作周报

> 覆盖：实际起止与时区；范围：实际项目；性质：正式报告/有限试写

## 本期结果与关注项

简述最重要的进展与仍需处理的问题。

## 这周具体做了什么

### 实际日期 · 事项

**工作**：具体调查、修改、实验或已确认决定。

**结果**：可复核的产物/结论。[E1](#e1)

**验证与限制**：实际验证层级，失败与未完成项。

## 任务增量与未完成

按事项说明本期推进、当前阶段和阻塞；不复述整段任务历史。

## 已确定下一步与待确认

已明确计划与新建议分别写，不擅自填负责人/期限。

## 证据与覆盖

证据编号、实际来源定位、代码/结果版本、原证据时间、覆盖缺口。
```

日期精度按原证据；只知道周范围就归到“本期、具体日期待核实”。过去完成但本周无新工作的事项只在背景中引用，不能充当本周产出。成功率、请求数、吞吐等保留分母、单位及条件，不拿名义配置当实测值。

## 项目与知识库改进周报

先列本期已实施变化，再列待验证/待确认项。每项用独立事项段落：**原问题 → 本期变化 → 作用与验证 → 状态/限制 → 证据**。短对照可用“此前/现在/证据”三列表；解释较长就用段落，避免单元格里塞整页文字。

- 项目改进：工具、流程、skill入口/职责、依赖等真实增量；有实测才写量化收益。
- 知识改进：具体新增判断、补齐条件、纠正什么、如何合并；历史保留在哪、为什么修订或过期。没有变化就如实写。
- 来源与发布：手工/其他会话/自动维护按可查证事实说明，未知不猜；逐项区分未提交、已提交、已核实推送。发布细节用文件组、实质变化、验证和SHA，不以文件数代替内容。
- 待确认建议：与已实施变化分区。skill候选引用现有评估产物及最小diff；旧候选已被当前手工修改覆盖时标已覆盖，不继续推荐。

两份周报中相同事项：个人版讲实际做过的动作，改进版讲前后变化与可复用价值，通过链接对应。不把自动化任务的运行次数当作项目收益。

## HTML与打印

Markdown是正文维护源，渲染器只负责呈现。HTML首页包含覆盖区间、报告性质及两份报告导航；桌面正文保持适当行宽，窄屏改为单列。颜色只作辅助，状态仍需文字表达。无需联网字体、远端图片、复杂图表或隐藏主体内容的折叠交互。

打印时去掉导航与底色，第二份报告另起页，表头可重复；长事项允许跨页而不出现空白整页。重要结论、表格、待确认项与中文长路径不能溢出边界。生成后至少查看桌面首屏、窄屏和打印版代表页；内容完整性与排版质量分别报告。

最后检查：首屏有结论与限制；两份目的不同且有具体事实；失败/待确认没有被美化成完成；证据可对应；没有样例占位、无依据图表、只有摘要的正文或任务记录混入公开发布。
