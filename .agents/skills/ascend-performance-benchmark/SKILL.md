# 服务性能压测

遵循[项目规则](../../../AGENTS.md)与当前任务授权。默认优先调用固定来源的 `aisbench_auto_tools_prefix`；用户指定其他工具或负载不适用时按需求选择，记录实际工具。服务部署、资源与远端执行仍复用已有入口。

## 输入与执行

1. 读取任务已有服务入口、模型/tokenizer、负载、并发、请求数、速率、流式与否、重复次数和前缀要求。只澄清影响实验的缺项，记录单位和正式测量条件。
2. 核对当前服务与客户端环境，确认没有冲突测量。请求端复用可用工具；压测只发负载，不自动重启服务。需要准备或修复服务时转原部署流程。
3. 使用 AISBench 工具时读取[配置与调用细节](references/aisbench-auto-tools.md)，按实际任务准备可写副本和配置，显式启动负载；上游依赖保持只读，不将请求端环境升级扩展到服务端。
4. 核查正式阶段的原生请求结果、成功/失败数和实际token统计，再交付TTFT、TPOT、吞吐及日志。前缀比例与实测缓存命中率分别报告，预热和正式阶段分别记录；仅外层退出0不能证明测量完成。

## 结果与后续

按[统一测试登记规范](../../../docs/task-records.md#aisbench-总表)判断本轮是否进入本机 AISBench 总表，登记正式测试的编号、包含硬件型号和机器部署情况的用途、前置关键结果及后置复现材料。完整命令/config、工具及数据集身份、原生结果和日志按同编号分组保存；失败和无定论保留。用户要求多组时逐组汇总再聚合，服务按任务生命周期要求保留。内部调优筛选及精度诊断沿用所属任务记录。

需要采样时调用原profiling入口，采样轮与纯性能轮分别记录；需要基线/候选回归判定时按[能力映射](../../../upstream/skill-mapping.md)使用原 performance-regression，确保条件可比，不凭一次吞吐测量宣称优化有效。精度问题和算子打流分别回到对应入口。
