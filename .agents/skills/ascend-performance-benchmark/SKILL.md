# 服务性能压测

遵循[项目规则](../../../AGENTS.md)与当前任务授权。默认优先调用固定来源的 `aisbench_auto_tools_prefix`；用户指定其他工具或负载不适用时按需求选择，记录实际工具。服务部署、资源与远端执行仍复用已有入口。

## 先区分执行与补录

- 新发起压测时走下面的输入与执行流程。
- 仅查看、汇总或补录已有结果时，走[已有结果的采集分支](../../../docs/guides/task-records.md#已有结果汇总与补登记)，优先读取原生汇总和必要配置。运行身份、指标口径及字段已足够登记时即停止，不进入压测准备或发起流程；缺项按该分支有界补证，不默认扩展为日志排障。

## 输入与执行

1. 读取任务已有服务入口、模型/tokenizer、负载、并发、请求数、速率、流式与否、重复次数和前缀要求。只澄清影响实验的缺项，记录单位和正式测量条件。
2. 核对当前服务与客户端环境，确认没有冲突测量。请求端复用可用工具；压测只发负载，不自动重启服务。需要准备或修复服务时转原部署流程。
3. 使用 AISBench 工具时读取[配置与调用细节](references/aisbench-auto-tools.md)，按实际任务准备可写副本和配置，显式启动负载；上游依赖保持只读，不将请求端环境升级扩展到服务端。
4. 核查正式阶段的原生请求结果、成功/失败数和实际token统计，再交付TTFT、TPOT、吞吐及日志。前缀比例与实测缓存命中率分别报告，预热和正式阶段分别记录；仅外层退出0不能证明测量完成。

## 结果与后续

按[三类正式测试登记规范](../../../docs/guides/task-records.md#三类正式测试总表)将正式性能运行写入本机性能测试表，直接填写 TTFT、吞吐、成功/总请求数等该类型指标及复现入口。按本轮范围保存命令/config、工具及数据集身份和原生结果；新发起测试保留其客户端运行日志，已有结果补录按上述采集分支处理，缺失信息如实标明。失败和无定论保留。接手手动启动的正式测试而无表项时先补登记并关联分析；调参排障及内部筛选留所属任务。精度与 SWE 分别走对应表和实际评测入口。用户要求多组时逐组汇总再聚合，服务按任务生命周期要求保留。

需要采样时按[当前运行体系](../../../upstream/skill-mapping.md#运行体系与执行入口)选择兼容的profiling入口，采样轮与纯性能轮分别记录；需要基线/候选回归判定时，先按[AISBench到回归工具的交接约定](references/aisbench-auto-tools.md#与性能回归工具交接)整理实际结果，再使用能力映射中适用的 performance-regression。确保条件可比，不凭一次吞吐测量宣称优化有效。精度问题和算子打流分别回到对应入口。
