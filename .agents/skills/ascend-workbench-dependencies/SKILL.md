# 工作台依赖维护

读取根 `AGENTS.md`、本次使用的能力、`upstream/sources.lock.yaml` 和存在的 `config/workbench.local.yaml`。配置与 lock 对应关系见 [共享配置约定](../ascend-workbench-init/references/config-schema.md)；升级图与具体核验见 [依赖检查约定](references/dependency-check.md)。

本 skill 维护直接依赖的选择与受影响链路。下层原声明是约束权威源，上层只存引用和检查证据，不建设第二套 pin、执行服务、身份或资源状态。

## 选择检查范围

- 日常任务只核对本次能力实际使用的依赖及环境，不默认 fetch 或查最新所有生态仓。
- 版本检查先只读核对 path、真实 Git 根、remote、完整 SHA、dirty、声明和实际接口。目录存在或旧 status 不代表能力可用。
- 明确升级时，先读候选父提交的声明，再给出目标组合与验证方案；本轮已授权升级步骤直接推进，提交/推送遵守根规则。不能把“检查升级”当切版本授权。
- 正在运行的实验、业务分支和共享 provider 状态保持稳定。业务组合可以核对，但工具升级不自动 checkout/reset 业务仓或 `submodule update --remote`。

## 从父版本构造受影响依赖图

对 lock 的 `sources.workspace/cannbot/matt` 及本次相关能力，记录当前与候选父 SHA。读取目标父的 `declared_dependencies` 引用、实际依赖文件、gitlink、脚本/参数/结果协议和环境要求；不能先启动旧父的 bootstrap 再猜目标约束。

每个相关节点记录：父依赖/父 SHA、声明文件、用途和启用条件、期望约束、实际路径/版本、拟用版本、检查结果与验证引用。递归读取可访问声明，按真实来源/环境/路径去重，检查同一节点的冲突与循环；不可访问项明确写出文件/父版本缺口。

- workspace remote-dev/coordinator 用目标 workspace 的原声明与原 status/bootstrap 入口。
- knowledge conformance kit 是可选测试依赖，只在相关测试/CI 启用时准备；缺它不阻塞无关运行。
- vLLM-Ascend/vLLM 的声明配对单独核对完整双 SHA 与实际分支；旧开发分支的偏离记录原因，不随领域 skill 升级自动调整。
- Python/DSL、CANN、torch_npu、镜像与芯片按本次任务兼容条件检查；不因资料升级安装或整体升级环境。

涉及原生依赖安装来源或 ABI/退出兼容问题时，可按需使用 [产物清单与原生探针](../../../docs/runtime-tools.md)，核对实际文件、模块来源、可用的已加载库路径及子进程最终退出状态。字节相同不证明运行兼容，正常导入也不证明模型可用；纯声明/版本检查不自动运行探针。工具不实施动态库替换或预加载修复。

## 升级与验证

1. 对比当前/候选父 diff，列受影响节点、接口和验证矩阵。纯方法改动做代表行为检查，脚本/协议改动检查实际参数/结构，必要运行验收按目标环境执行。
2. 准备候选约束要求的下层版本，使用可隔离候选目录或原工具支持的定向入口。旧 bootstrap 按旧 pin 工作时不能用它声称准备了目标 pin；不改下层维护源，也不破坏共享在用 checkout。
3. 验证候选父与下层组合。required 接口缺失、冲突、循环或不能验证时只暂停受影响切换，保留原组合并给出范围/验证选择；可选未启用项标记 not_enabled。
4. 全部受影响必需检查通过后切换已验证组合，核对真实父/子 SHA 与能力入口。保存旧组合、定位方式与回退条件，更新顶层 gitlink/lock 及权威记录；只对已授权范围执行，提交/推送单独遵守授权。

满足父约束不等于拉到每个项目最新 main。显式开发偏离可以记录版本、原因与兼容证据，不把参考 pin 自动升级为所有任务的硬门禁。branch=main 不授权业务子模块更新。

## 交付与恢复

输出实际/目标版本、受影响图、能力结论、验证层级、未执行项、回退信息和下一步，更新工作台开发记录及相关来源/能力映射；具体业务状态仍在任务说明。静态检查、模拟演练和真实环境验收分开报告。

必要准备可复用 init 的定向操作约定与现状，不能调用完整 `$ascend-workbench-init`；初始化也不为补配置运行完整升级。失败恢复先查现状与原失败，只补本次受影响步骤，保留正在运行的实验与底层原记录引用。
