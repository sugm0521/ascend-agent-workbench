# 任务计划与动态分工

## 共用上下文

作为共用模块按需使用，复用同一任务、领域和有效知识查询。新增目标/错误/条件变化才按[共用约定](../../../docs/guides/skill-routing.md)补查，不重复问卷或建立第二份状态；专业方法由领域/具体能力提供。方法来源见[消费声明](references/upstream-usage.json)。


遵循 [根规则](../../../AGENTS.md)；复杂分工或恢复定点读 [框架第 8–9 节](../../../docs/maintenance/项目框架.md)。输入是当前目标、用户授权、验收条件与可查证的代码/环境基线，输出是任务说明中的计划以及必要 assignment。

## 建立可执行计划

先核对目标是否充分明确。缺少事实自己查证；缺少取舍仅补问会改变方案的部分。只有规划授权时交付计划，不把计划中的动作视为执行授权。

把工作拆为具有独立产物和完成标准的子任务，不按文件数量或固定角色拆分。每项记录 id、目标、负责人、输入引用、允许写入范围、依赖、资源需求、验证/完成标准、状态和结果位置。先安排能验证关键路径的最小闭环，再补足必需覆盖；不以闭环已通代替完整验收。

依赖图须无环，只派发输入与权限均已就绪的工作。下游需要上游结果时先取得可核查产物；同一个根因或共享状态紧密关联的调查可由一个 agent 连续负责。涉及修改的计划在实现早期安排覆盖摘要、逐轮回归与最终集成；只读任务安排证据复核，避免写成修复验收。

计划保存在 `任务说明.md`，主 agent 独占整体状态与全局决定。计划修改递增 `plan_revision` 并记录原因；assignment/结果绑定稳定 task_id、子任务 id 与 revision。旧版本结果若可复用，写明当前条件下的依据。

## 选择委派或主线程执行

仅在独立工作或独立复核收益能抵消协调成本时委派。默认一层、最多三个同时运行的子 agent，并服从实际工具限额；子 agent 不继续委派。无委派工具时主 agent 执行并说明限制。

按[统一材料规范](../../../docs/guides/task-records.md#任务目录与唯一入口)，每个实际委派使用 `results/assignments/<子任务编号>-用途/委派说明.md` 和 `结果.md`；后续反馈在同一结果文件按轮次或计划版本分段。assignment 包含：

- 身份与目标：task_id、子任务 id、plan_revision、交付物和完成标准。
- 已定事实：必要资料入口、代码/环境基线、用户决定及授权范围；已有验证通过的配置、用例或模板注明适用条件。条件仍成立时复用；条件变化影响有效性时，按差异调整并验证受影响部分。
- 边界：可写文件/业务 worktree、只读资料、依赖、设备/端口/服务需求及禁止扩展项。
- 发布边界（涉及拟入仓产物时）：拟发布文件、本机输入仅供调查的范围、公开参考/声明依赖与适用复用验收，按[统一规则](../../../docs/maintenance/validation.md#开发与发布的跨机器复用规则)组织；本机报告及索引只回传到本机任务，不随公开结果传播。
- 回传：结果位置、验证证据、限制、下一步和底层 task/session/run/execution 引用；已委派的长任务在关键进展、失败或需要用户纠偏时及时回传，由主 agent 向用户同步。

只读 assignment 可允许写自己的结果文件，不能因此修改业务源码。交叠写入串行处理或使用已授权隔离 worktree，最终由主 agent 整合并验证；不要让子 agent 修改整体任务说明、另建全局计划或各自推送。

NPU、端口、服务和远程 session 使用底层现有协调机制。上下文隔离不能证明资源隔离；同一 NPU 性能测量先协调实际占用。执行资源不足时调整顺序，不创建第二套租约或 SSH 状态。

## 接收结果与修订

要求简洁返回结论、改动、实际验证、证据入口、限制和下一步；大日志/源码保留引用。主 agent 核查关键证据与终态，不能只拼接摘要。“已启动”保持运行状态，直至完成或明确阻塞。

冲突、输入变化或结果推翻假设时修订计划并通知受影响负责人；保留原失败和旧 revision。中断交接记录当前 owner、就绪前沿、代码/环境与底层运行。接手后先核查实际状态，确定唯一 owner，再续派已就绪工作。
