# 工作台初始化

作为唯一总入口，把现状、用户选择和下层定向步骤合成一份计划。首版由 agent 读取 YAML 与 Markdown，再调用已有工具；本 skill 不提供新的初始化服务、通用 CLI 或第二套执行状态。

## 先确定范围

读取工作台根 `AGENTS.md`、`README.md`，以及存在的 `config/workbench.local.yaml`、`upstream/sources.lock.yaml` 和 `.workbench-local/init-report.md`。配置字段与缺省语义见 [配置约定](references/config-schema.md)；操作、下层工具与验收见 [初始化操作约定](references/operations.md)。

- 标准模式准备两个业务仓库、作者、GitHub 身份、认证通道、拓扑与 PR 条件，并完成所选下层消费方式对应的初始化；执行组件与服务器接入分别确定范围。将[知识库接入选项](references/operations.md#私有知识目录接入)一并纳入集中确认：是否启用、本机目录、远端新建/复用/不使用、定时维护与同步策略分别选择。沿用已有选择，不要求特定笔记软件或 Git 托管。
- 用户明确只做资料/分析准备时采用轻量模式，并列开发缺口。
- 用户只要求知识库接入、补齐远端/定时选择时，定向执行知识接入分支；不准备无关业务仓、依赖或远程环境。
- 没有本机配置时先只读探测。示例里的路径和偏好不是已确认的业务绑定或授权；集中补充关键未定项后执行已授权步骤。
- 已有选择与本轮授权直接沿用；账号、分支、既有 remotes、fork、SSH key 或新增范围的变更需具体授权。遵守根规则中的提交/推送边界。
- Git 推送大小策略按[配置约定](references/config-schema.md#git-推送策略)核对：首次初始化必须在集中确认中询问“不限制，还是设置上传字节上限”，选择限额时收齐正整数字节数；无明确答复则标记pending_decision，不把示例/null当作已确认。可核实的既有用户决定直接沿用；恢复保留已有选择。报告有效值，不用实际推送测试限制。
- 新服务器接入按[免密接入约定](references/operations.md#新服务器免密接入)执行；用户已确认默认补齐现有公钥时直接沿用，不重复逐台审批。缺身份或首次凭据只澄清缺项，普通清单/查询不触发公钥写入。
- 用户只要求服务器清单/可达性刷新时，仅执行[保存目标发现](references/operations.md#保存目标与-npu-接入)，按[服务器总表](../../../docs/task-records.md#服务器可达性总表)记录带时间的快照，不运行完整初始化、创建运行或接管原资源状态。日常代码更新使用 [repository-update](../ascend-repository-update/SKILL.md)。

## 先汇总下层初始化要求

**下层仓库也需要初始化，clone 完成不代表接入完成。** 首次初始化先逐个读取启用来源的根规则、README、初始化入口与相关传递依赖声明，形成 [下层初始化清单](references/operations.md#下层初始化清单)，再向用户集中确认；不能只列上层业务仓选项，实施时才逐层补问。

按实际用途列出资料/方法引用、workspace 本机身份/profile、直接远程工具、任务协调、服务器/容器和测试的必需状态及取舍。workspace 用于工作区工具时，本机资源用户名与统一 alias 是下层选择，不能因尚未连接服务器而遗漏。cannbot/Matt/model_analysis 的资料消费无需全量插件安装；原生插件或工程流程选中后才补其真实配置要求。

用只读方式核对本机平台、现有工具/provider/SSH、本轮父提交的 pin 与所需接口。版本不可获取、仓库迁移或平台不适用时，在确认方案中列具体缺口与可验证替代，不能静默改最新版本。已有远程工具可复用，但实际接口、身份与状态归属必须适用，不能只凭名字相同认作同一 provider。

## 核对现状与唯一目标

1. 用只读 Git 查询核对实际 Git 根目录、branch/detached、完整 SHA、dirty、tracking、作者及其来源、remotes 和 fetch/push 配置。未初始化子模块回落到父 Git 根目录时，标记缺失，不能作为独立仓库操作。
2. 以环境上下文和真实工作目录去重。路径别名合并，不同 worktree 的工作目录状态分别核对；不同主机或容器的同名路径不合并。
3. 每个业务仓库只绑定一个实际路径：复用、专用 clone、workspace 业务子模块可以混合选择。默认优先复用；已确认专用 clone 后按该选择准备。`repos/` 或外部绑定不再准备 workspace 的另一套业务副本。
4. 分别核对 Git 作者、GitHub 登录、Git 认证和各仓库推送权限。正确已有状态复用，不能用同一登录代替两个仓库的权限检查；不用实际 push 测权限，不输出凭据。
5. 先读下层脚本的入口和副作用。workspace 的 `repo_init_probe.py` 和 `repo_init_profile.py plan` 会确保持久身份，不能当纯只读探测。分支总览用 Git 查询；provider/profile 只在启用相关能力时准备。

## 一份操作表推进缺失步骤

在本机报告中列每项操作的目标、期望状态、单一执行方、依赖、授权、状态和证据。上下层需要同一变化时合并；委托下层后上层只验收，不并行再做一次。

### 实施前确认

只读探测和上下层清单完成后、首次实施有副作用的初始化操作前，必须完成一次集中确认。首次初始化必须询问Git上传大小策略（不限或指定正整数字节上限），已有明确用户决定可直接沿用。汇总可选知识库的本机目录、远端模式、定时维护及同步策略的全部适用未定项，以及两个业务仓的路径、来源/拓扑、基线/配对、作者/账号，及适用下层的资源用户名/alias、工具/provider 消费方式、版本替代、客户端接入位置和已选服务器/容器方案。先说明哪些能力本轮准备、哪些不启用，再收齐所有必需未定项；配置默认 false 不代表用户已选择跳过下层。已确认或已有可用配置直接沿用，明确未启用的能力不要求无关信息。

**全部必需项得到明确答复或可核实的既有决定后，才能开始本轮初始化实施。** 异步或分组问题只收到部分答复时，保留已回答选项，将未回答项标为 `pending_decision`，等待剩余答复；不能因为代码路径已确认就先 clone、切分支或初始化依赖，把作者等其他必需项留到最后。未提交的预选项、默认值、沉默和等待时长都不代表答复。

等待期间只做资料读取、只读 Git/API 查询、方案整理和必要任务记录；不运行 clone/submodule update、作者/remotes/本机配置写入、登录/安装/profile/provider bootstrap 等初始化实施操作。检查脚本若会创建持久身份，也须经过确认。用户明确缩小本轮范围后，只对新范围重新判断必需项；不能自行把标准模式降为轻量模式以绕过等待。详细确认项与验收见 [实施前确认约定](references/operations.md#实施前确认)。

### 按已确认方案执行

1. 首次实施保持全部必需选择齐备的门槛，把已定选择、授权和范围传给下层，避免重新确认。重复初始化/恢复只补新增未定项；实施中出现新必需选择时暂停依赖该选择的操作，先补充确认，保留已完成结果，独立准备与验收可继续。
2. 按 lock 初始化选定顶层 `deps/` 路径，默认非递归。不能无差别运行整个 `deps/` 的递归初始化；限定递归前查明其会创建哪些业务或可选仓库。
3. 只执行待办：复用已有 checkout，或从已确认远端正常克隆到专用路径；不覆盖冲突目录，不把软链接/worktree/shared objects 冒充独立 clone。配置缺失作者时只写已确认仓库级设置，认证共用状态只准备一次。
4. 新业务组合先确定 vLLM-Ascend 基线，解析该提交的 CI-pinned vLLM，再获取并核对真实提交。`status: ok`、目录存在或解析出 ref 不代表完成。报告完整双 SHA 与声明来源，拓扑步骤不得再把配对切回 main。既有开发分支只核对偏离，不自动切换。
5. 下层仅接受已分配步骤。它不支持范围/外部路径时用适用定向 helper；无入口则说明缺口与适配方案，不自动全量 init、改下层维护源或新建下层 skill。
6. 已选择知识库接入时，按[私有知识目录接入](references/operations.md#私有知识目录接入)只补齐已确认的目录、私有远端与维护任务；本机绑定仍用唯一 `paths.knowledge_root`，远端与调度选择留本机配置。未选择的分支不实施。
7. 执行后重新核对实际路径、配置与版本。失败保留原结果；重试仅补缺失/失败项，未知中断先查证。成功项不重复 clone/login，缺失只阻塞依赖它的能力。

使用已有 SSH 发现远程环境时按 [保存目标与 NPU 接入](references/operations.md#保存目标与-npu-接入) 探测。仅加入连接、硬件与目标环境验收通过的 NPU 目标；无 NPU、不确定和不可连接分别记录。探测授权不自动授权新建容器、安装环境或启动任务池。

初始化不自动升级已用依赖；版本变化交给 `$ascend-workbench-dependencies`，两者共用现状与 lock，不能互相调用完整流程。底层身份、provider、pin、task/session/run/execution 与设备/端口状态仍由原工具管理，上层只记录引用。

## 完成与接入

为业务仓准备开发/PR条件时，按[预检环境发现约定](../../../docs/business-ci-preflight.md#环境发现与隔离)只读识别本机或已登记Linux检查环境，在现有初始化报告记录平台、工具版本、认证/provider引用、用途和查询时间，分别标明静态检查与CPU用例的可用性及缺口。CPU/Linux环境不要求NPU就绪；SSH配置或密钥存在只说明有候选，不证明连接与环境可用。不在初始化运行业务测试、上传业务快照或擅自安装系统依赖，逐轮预检重新核验即可，不重跑完整init。

将实际模式、路径（包括可选 `paths.knowledge_root`）和已定选择保存到忽略提交的本机配置；报告分别验收资料/skill、代码、作者/GitHub、下层本机身份、直接工具、协调能力与远程目标。provider 的源码、启动、接口枚举、实际调用、客户端加载分别验收；不能以 tools/list 成功冒充功能可用。平台缺口不能自行转成安装 WSL、迁移协议或部署服务，新增选择先确认，已就绪的独立能力继续交付。

报告包含带查询时间的仓库分支总览与依赖声明偏离。默认不为总览 fetch，ahead/behind 写明引用新鲜度。保留工作台为 Codex 主目录；按需附加两个实际业务目录，分别记录“agent 可访问”与“界面已附加/待操作”。clone 不等于界面登记。原生主仓 PR/worktree 操作不能误用到业务代码，业务 Git 操作始终指定实际 repo/worktree。
