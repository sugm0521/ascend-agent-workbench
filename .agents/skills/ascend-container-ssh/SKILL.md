# 容器独立 SSH 登录

遵循[项目规则](../../../AGENTS.md)。交付可从用户指定访问端登录的容器SSH入口，复用现有远程执行能力；不建立另一套机器、身份或端口管理状态。

## 锁定目标与认证

- 从当前任务、实际容器清单和用户指示确定宿主、容器、账号、访问路径、认证方式与本轮授权。明确要求配置即在该范围内推进；复用已确认值，只补问影响执行且无法查到的缺失项。仅检查时不改变配置或凭据。
- 先核对容器是否运行、网络模式及已有sshd。通过执行工具的明确容器目标或宿主侧inspect + exec锁定容器；容器标记和namespace用于交叉验证。`command -v docker`不能单独证明执行位置，容器内可能也有Docker客户端。
- 托管目标只识别并交接其原SSH契约、端口与修复入口；完整机器接入/ready请求交[machine-management](../../../deps/vllm-ascend-workspace/.agents/skills/machine-management/SKILL.md)。仅SSH请求不调用完整bootstrap/readiness来代替有界修复；原工具若只能运行整套初始化或NPU smoke，说明额外副作用与所需授权范围，不复制第二套托管流程或覆盖密钥策略。
- 密码、公钥和登录账号按用户选择或既有有效配置使用；没有通用密码或固定端口。密码经安全输入、内存和加密连接stdin传递；按已确认的[本机容器总表规则](../../../docs/task-records.md#容器总表与最小环境记录)，容器 SSH 明文口令只持久记录在忽略的本机总表，不写入命令参数、生成脚本、聊天、任务报告或日志。配置口令与宿主登录凭据分开。
- 用户已授权默认补齐免密时，对本轮要求接入的目标账号沿用[现有公钥追加和新连接验证规则](../ascend-workbench-init/references/operations.md#新服务器免密接入)，不重复询问；仅检查入口不触发写入。容器授权文件与宿主分开，托管目标继续交原工具，不借此重配宿主。

## 确认对外入口与可用端口

| 网络方式 | 检查与选择 |
| --- | --- |
| host网络 | 容器和宿主共享端口；检查宿主实际监听及端口协调记录，优先复用属于目标容器的可用入口，否则在允许范围内找空闲端口 |
| bridge / 已有端口发布 | 核对宿主地址:发布端口 → 容器SSH端口的实际映射，分别检查宿主发布端口与容器内部监听 |
| 其他网络方式 | 使用原提供者确认的入口与分配机制，不假定修改sshd端口就已对外暴露 |

多机可优先找共同空闲端口，没有共同端口时按实际约束分别选取并报告。用户指定端口被其他组件占用时，不停止该组件；说明冲突或按其授权换用空闲端口。

创建前在实际监听地址/地址族上确认可绑定，启动前再检查以处理探测后的竞争。缺端口发布时保留入口缺口；SSH配置请求不自动授权重建容器、修改宿主防火墙或添加转发。已有目标入口通过验证且符合本轮要求时直接复用，不重复重置密码或重启sshd。

## 配置并启动

在已核对的容器内执行；缺sshd时仅按本轮已授权的容器依赖准备路径处理，缺权限或来源只阻塞该目标。

1. 确定该sshd实际使用的配置文件和PID文件并备份。用户给出命令时保留其已定参数，将端口替换为实际选用值。
2. 按账号及认证要求落实Port、PermitRootLogin、PasswordAuthentication、PubkeyAuthentication、UsePAM等适用项。不把一次任务的认证项变成通用默认；不无条件覆盖整个配置或其他认证策略。
3. 生成缺失host key、准备运行目录，先通过`sshd -t`；再用`sshd -T`核对有效端口与认证项。有Include或Match时核对相关展开/连接条件，避免文本已修改却被其他规则覆盖。
4. 在授权范围内更新密码或公钥。密码可通过内存生成的`账号:密码`文本送入`chpasswd`的stdin；实际凭据不进入保存的命令模板。
5. 需要替换原daemon时，在停止前核对PID仍是sshd且属于目标容器及该SSH入口，PID文件只是线索。不能仅凭旧PID文件、进程名或端口号kill宿主/其他容器进程；归属未知先查证。
6. 使用容器原有管理方式启动sshd。采用`nohup sshd -D -e`时关闭stdin、保存有界日志并核对启动退出/存活状态。若端口被抢占，回到端口选择，不清理未知监听者。

失败后查清已发生的副作用与当前daemon状态，必要时仅恢复本轮已备份的配置；不能宣称未掌握原凭据的密码变更已回退。不在未知中断状态下重复配置、循环重启或自动改宿主网络。

## 验证与交付

- 核对实际监听地址、端口、daemon及其容器归属。host网络可由宿主监听PID的mount namespace与目标容器交叉验证；不能只看端口开了。
- 从用户计划使用的访问端，用指定认证方式完成一次实际SSH登录；校验服务器host key与通过原可信路径取得的目标信息，登录后核对账号和目标容器标识，namespace可比时一并核对。
- 登录失败时按实际证据区分daemon、端口发布、访问网络和认证问题；逐目标报告成功/失败与恢复条件。仅本地监听、banner或容器内连接成功时，不能宣布对外登录通过。
- 交付每台宿主/容器、连接地址与端口、账号、认证方式、实际登录结果、配置备份和服务生命周期；不重印密码。仅nohup启动不承诺容器重启后的自启动，持久入口变更按用户另行给定的范围处理。
- 首次实际使用时登记容器总表，安装/替换 SSH 依赖时更新环境变更项；同步实际对外入口、端口、账号、认证方式和已知密码。SSH 配置及验证细节放所属任务结果，总表提供入口；不扩大为全量历史盘点。
- 验收止于SSH入口与归属，不将其当作模型或NPU运行就绪，不顺带部署服务、升级业务依赖或执行模型测试。

可直接调用：`$ascend-container-ssh 给指定容器建立独立SSH登录入口，找空闲端口并验证登录。`
