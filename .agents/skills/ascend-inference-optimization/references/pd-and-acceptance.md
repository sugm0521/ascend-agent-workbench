# PD 指标、环境复刻与验收

## 每 D 卡输出吞吐

用户指定 AISBench `Output Token Throughput` 时，使用本次完整正式 run 的原生字段及其实际单位；记录 AISBench 版本、字段来源和统计窗口。不用 Total Token Throughput、请求吞吐、D 端局部计数或带 profiling 的值替代。

```text
output_tokens_per_second_per_D_card = native_output_token_throughput / allocated_D_cards
```

`allocated_D_cards` 来自实际参与这次端到端负载的全部 D worker 的物理 NPU 卡并集。按节点、设备身份及角色去重；TP/DP/PP/EP/CP 可能共享同一组卡，不能直接把全部并行维度相乘。没有收到请求但已分配给该方案的 D 卡仍计入，不能事后只计算繁忙卡。若平台一个物理卡暴露多个逻辑设备，先核实用户所说的“卡”及逻辑到物理映射。

例如一个完整 run 的原生输出吞吐为 6400 token/s，实际 D 分配 32 卡，则归一化结果为 200 token/s/卡。这只是算术示例，不是任何模型的性能承诺。

同时保留 P 卡数、P/D 拓扑、代理和传输路径。P 处理或 KV 传输可能限制 AISBench 看到的整体吞吐；按 D 卡归一化不能证明瓶颈一定在 D。增加 P 资源会改变部署成本，改变 D 卡数会改变分母，均需单列。

从用户既有配置/结果恢复正式负载及缓存策略；存在多个性能尝试时按用户指定方案选择起点，保留其他尝试及失败。不能通过缩短输出、改提前停止规则、增加未声明前缀、隐藏失败请求或更换负载获得表面达标。

判定前检查：原生 run 完整，成功率与输出完整性满足任务要求，D 卡分母有实际证据，负载和质量要求一致，重复结果与波动按已定标准判读。没有约定聚合口径且结果在目标附近波动时，同时报告逐轮结果与统计量，保留结论待确认。

## 复刻已有容器

当下一步依赖“完整复刻”时，从源容器只读收集以下覆盖，分清容器可写层与宿主挂载：

- 基础镜像不可变 digest/平台，容器创建参数、设备/网络/IPC/ulimit、挂载源及容器路径。
- 驱动与用户态 CANN/HCCL、Python/torch/torch-npu，vLLM/vLLM-Ascend 实际 checkout、dirty patch 和 editable 映射。
- FlashMLA、FLA、Mooncake/HIXL 等本次实际使用的 wheel/原生库及覆盖安装，动态库搜索路径、环境变量和启动脚本。
- 业务配置、模型/tokenizer 可访问性、必要编译缓存和外部服务；按相关性收集，不默认打包整个运行文件系统。

最新镜像的 tag 查询只能给出下载候选。固定平台 digest 并核对创建时间、版本与源容器差异；如果源容器基于更早镜像且已有热补丁，先判断哪条复刻路线能恢复同一执行条件。

通过[复现清单](../../ascend-runtime-snapshot/SKILL.md)和[产物工具](../../../../docs/tools/runtime-tools.md)分别验证版本/文件覆盖；在任务副本中执行必要的原生导入、功能与真实 PD 路径验证。每台目标独立验收。文件相同、能 import、服务可用和性能一致是不同层级，未知差异不能写成“完全复刻”。

大型镜像/模型/wheel 留在远端，通过符合用户传输限制的既有远端路径获得；本机发送脚本、文本和命令也要检查载荷大小。不能用大仓自动快照绕过上限。必要凭据只交给既有安全输入/认证能力，不写入 skill、任务文档或日志。
