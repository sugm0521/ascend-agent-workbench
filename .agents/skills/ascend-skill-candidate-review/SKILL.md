# Skill 候选改进评估

遵循[项目规则](../../../AGENTS.md)。本 skill 只负责筛选与收敛候选，已授权实施交给[skill-development](../ascend-skill-development/SKILL.md)。用户已说明的约束和授权沿用，不让用户反复强调轻量化，也不为评估启动完整工程流程。

## 用证据筛选

只读目标 skill、相关引用/工具和直接关联的任务证据，不全量扫描 skill、历史或环境。先明确要纠正的具体错误、遗漏或重复劳动，再对照已有覆盖；一次严重且可查证的缺口可支持窄修复，单次实验脚本不自动支持通用工具建设。无证据的假设不变成默认检查。

优先选择：不改或复用现有能力 → 合并/替换已有说明 → 在现有 reference 增补有触发条件的分支。只有稳定的重复需求与收益足以抵消依赖、日志、测试和维护成本时，才推荐公共脚本或新 skill；即使用户授权新建，也避免与原入口重复维护职责。具体主机、路径、版本症状保留在任务证据，不固化成通用流程。

## 最小必要增量

- 不为“改进”凑候选、数量或完整性；已有规则能合理覆盖就明确不改。不要把每次失败叠成新规则，重叠内容合并或引用，过时内容可提出替换。
- 每个新增检查必须说明**何时触发、解决哪个判断、何时足够停止**。无法说明则不加入；正常路径复用原流程，异常排查按证据逐步展开，不默认全量扫描、源码插桩、配置/hash审计或额外实验。
- 新增检查先消费现有有效证据，只有缺失、过期或矛盾会改变结论时才采集。找到可用环境或定位到所需证据后回到原流程，避免重复初始化、另一套执行/资源系统或大范围升级。
- 精简的是冗余操作，保留用户必需验收、正确性与授权边界。隔离测试成功不冒充正式配置已修复，局部验证不冒充端到端通过；证据不足时限制结论，不偷偷降低标准。
- 优先最短入口，细节仅在确有需要时进入既有 reference。确定性重复操作才考虑脚本，纯文档修改不增加匹配措辞的测试；验证聚焦改变的决策分支与正常请求不误触发，不铺笛卡尔积或重跑无关远端实验。

## 交付与授权

输出少量值得保留的候选或“无需修改”，说明直接证据、已有覆盖、最小改动位置、触发条件、收益/成本与适度验证方式；已覆盖或暂缓项只简述理由。没有真实测量不声称节省token或提高性能。候选有价值不等于全部必须实现。

状态使用 proposed/approved/deferred/rejected/implemented；值得后续跟踪才按项目规则落到 `docs/reviews/`，任务状态沿用原任务说明，不另建重复清单。单纯评估只交付建议；已有明确创建/优化授权且范围已定时，按该范围接着实施，不重复请求批准常规编写与验证。扩大用途、改变必需标准或新增未授权副作用时再明确范围；提交/推送沿用项目审核规则。无新证据不反复推荐已拒绝候选。
