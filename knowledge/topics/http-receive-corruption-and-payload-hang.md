# 流式HTTP收包损坏与解析异常未传播

## 结论

压测停在少量请求未完成、`FAIL=0`且服务健康时，至少区分两层：响应字节为何损坏，以及客户端为何没有将解析失败转换为请求失败。增加模型或KV传输超时、升级压测包，都不能替代这两层的证据。

固定aiohttp源码的C解析入口抛出异常后关闭transport并设置协议异常；不能仅凭该操作认定已有业务payload的读取者已得到异常。[aiohttp-client-protocol] 历史现场与隔离实验中，出现HTTP头已成功返回、协议保存`Expected LF after chunk data`、transport已关闭，但payload无EOF/异常、读取Future仍pending。配合请求预算全部为None，最终聚合可持续等待。该现象不表示所有aiohttp版本、所有坏chunk或所有正常流都会挂起。

## 历史证据与不同结论的边界

原观察日期为2026-10-20，压测客户端时钟与采样端存在约13分钟偏差；以下按同轮请求ID、TCP序列和采样顺序关联，不直接以跨机墙钟相减归因。

| 证据层级 | 历史观察 | 支持的判断 |
|---|---|---|
| 多点原始字节摘要 | 5条失败请求在D发送与代理接收之间body一致；代理发送的相同序列范围正确，客户端接收末尾3–14字节改变并破坏CRLF | 变化位于代理发送抓包点之后、客户端HTTP解析之前；不能直接归因于模型或HTTP业务逻辑 |
| 接收小包复核 | 故障接收包IP校验正确、TCP校验错误；仅在隔离计算中换回发送侧正确payload后恢复TCP校验 | 收到的字节与其校验值不匹配；TX卸载产生的发送侧占位校验值不能用作相同证据 |
| 纯TCP单变量对照 | 128连接各12000帧，共351744000字节；RX校验卸载开启时4个坏帧进入应用，关闭后应用坏帧0，仍捕获1个坏包并约9.8ms后收到同序号正确重传 | 该环境关闭RX校验卸载后，软件校验与重传可保护应用数据；没有证明损坏源消失 |
| CPU解析隔离 | 原C路径坏chunk等待超过约300ms看门狗；补充payload异常传播后约11ms显式失败；74个合法分段点通过；有限预算对照也能退出 | 异常传播与有限预算是独立兜底，不负责修复收包数据 |
| 原负载回归 | 1280条请求均成功且各输出1024token、原生退出0；仍有11个坏接收包被软件校验丢弃，重组后全部响应body与代理发送侧一致 | 证明该次工作负载的结束与内容完整性；不证明语言精度、性能提升或底层硬件根治 |

本次复核重读1280条原生详情、核对关键小包与保存的统计；没有重新执行这些网络/CPU/模型实验，也没有全量重算多GB抓包。运行材料未公开，故案例保持candidate。AISBench升级前后均发生过挂起，旧轮的不完整成功计数不能作为完整基线。

## 可复用的复核方法

1. 将目标请求总数与原生逐请求详情、唯一ID、实际输出长度、退出码对应；pending不因失败计数为零而成为成功。
2. 读取稳定等待链，区分业务payload、协议、transport、请求预算和聚合Task。只读进程快照存在并发缺项时保留缺口，不能单靠最后一行进度判断死锁。
3. 抓包必须覆盖错误发生前；按请求ID、四元组和TCP序列范围关联，处理端口复用、缺口与重传。分别核对D到代理、代理发送到客户端接收；不跨TCP缺口拼接或以正常后半程排除早期错误。
4. 接收侧依据真实校验值及内核计数判断，发送侧先核对TX卸载。用纯TCP确定性帧隔离HTTP和模型，再在授权范围内做单变量网卡对照。
5. 同时检验错误显式传播、有限请求预算、合法流分段及原负载结束。历史600秒是每次HTTP尝试总预算，重试仍可能延长整轮时间，不是压测全局600秒截止。

历史规避是关闭客户端RX checksum offload，同时在解析错误路径唤醒payload并设置有限预算；这是有环境前提的运行修改，不能作为所有服务器的默认配置。网卡运行时设置可能随重启、驱动重载或网络重配失效；复用时需先确认当前状态、权限与性能条件。原本地补丁未作为通用补丁发布，不能直接套用到其他aiohttp版本。

## 限制与复查条件

没有定位到具体NIC、固件、DMA指令或链路设备故障；历史驱动已包含当时检查的两项已知屏障/排序修正，不能据相似症状宣称缺少它们。修复HTTP路径也不证明更早的Mooncake建链失败已解决；其分层预算见[Mooncake超时](mooncake-nested-timeout.md)。

aiohttp解析/关闭顺序、AISBench异常传播或预算、网卡/驱动/内核、卸载设置及代理拓扑改变时重新复核。客户端遇到`DONE`后主动结束可留下无终止零chunk的抓包；只有内容与接收契约同时核实后，才可将此与最初的非法chunk区分。
