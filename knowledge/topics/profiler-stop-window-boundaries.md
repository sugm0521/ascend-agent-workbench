# Profiler停止控制与实际数据窗口

## 结论与适用条件

“首条正式请求后N秒调用stop”只描述控制动作，不能直接把所有原生trace、DB和统计称为N秒。分布式profiler的停止RPC可能包含同步、排空和导出等等待，具体时间需由请求/响应记录和每个rank的原生metadata分别确定；不能仅从延迟数值推断是哪种机制。

本条保留已观察的窗口差异和分析口径。原始运行材料未公开，保持`candidate`；不宣称所有版本或负载都有同样延迟。

## 复核与裁剪方法

1. 分别记录start请求/响应、首正式请求、stop请求/响应及各rank原生起止；预热是否包含在内单独说明。用于控制间隔的单调时钟与日志墙钟也要区分。
2. 保留完整原始窗口，在副本中按明确锚点导出目标窗口；duration事件跨界时只保留重叠区间，并保留原始时间/时长标记。flow和关联事件按窗口规则检查，不能只截取kernel表后声称整个trace已同步裁剪。
3. 原生DB、通信统计或硬件counter没有同步重算时，继续标为完整窗口。边界duration裁短不能使原硬件counter自动变成该片段的数值，不能据此计算精确的窗口硬件利用率。
4. 多机各自起点加共同RPC偏移仅是一种对齐方法；未经独立时钟校准，不相减各节点绝对时间来计算精密跨机等待。

## 性能对照与不能推出的结论

纯性能轮与含采集/stop同步开销的轮次分别报告。测量中的差异只能先作为观察，不直接判定业务代码收益或退化。固定窗口内的stage设备工作段也不等于包含排队、输入等待和控制开销的完整RPC时延。

本条不要求每次普通性能测试都采集profile，不提供重新采集或清理历史数据的授权。任务已结束且无在途负载时，不能把随后打开profiler产生的数据回算为之前那轮的采集结果。

## 复查触发

profiler/RPC实现、并行规模、触发锚点、数据导出格式或裁剪规则变化时，重新核对实际窗口。获得原始数据后再验证边界事件、跨rank对齐与counter口径；缺少这些证据时保留限制，不用目标秒数替代实际时长。
