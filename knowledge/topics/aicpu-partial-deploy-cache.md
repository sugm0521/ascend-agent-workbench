# AICPU公共库部署不完整与缓存复用

## 结论与识别条件

`ACL stream synchronize failed, error code:507018`可能是此前异步AICPU失败的传播位置。只有在同轮、同设备、同进程中进一步找到`TFOperateAPI / libtf_kernels.so / 11002 / open so failed`，并取得loader的实际错误，才能判断是否接近本案例。单凭507018、AICPU字样或某个模型栈，不能认定库部署不完整。

2026-10-21历史调查中，原模型在视觉编码器预热的`cu_seqlens.cpu()`同步时报错，前序AICPU Slice已加载库失败；隔离StridedSlice用例取得`libtf_kernels.so: file too short`。宿主源包中的ELF完整，设备后续启动却按原压缩包哈希命中缓存并跳过部署。结合更早的设备复制页申请失败及部署错误处理机制，证据共同支持设备公共库部署不完整、缓存标记与实际文件不一致的故障链。

本条尚未证明设备库实际为0字节，也没有完成恢复验收；是有版本和证据边界的历史候选案例。

## 历史证据分层

| 层级 | 观察 | 能支持与不能支持的结论 |
|---|---|---|
| 原服务运行 | AICPU Slice加载TF库失败在先，CPU读回同步507018在后 | 同步是传播位置；不能据此改成通信建链超时 |
| 隔离NPU控制 | complex64实部/虚部路径通过；complex128实部contiguous触发StridedSlice并得到file too short；普通float64切片/clone通过 | 相同库加载故障可脱离模型权重复现；不能推断原模型使用complex128，也不是所有double或切片都失败 |
| 包与设备状态 | 宿主legacy包与原镜像内容一致、目标ELF可解析；设备loader拒绝库；包哈希比较仍命中skip load | 源包、解包文件、缓存标记是三个验证对象；包哈希不是逐文件完整性证明 |
| 设备黑匣子 | `Comm: cp`经shmem文件写入路径申请普通页失败，order 0、nodemask 32–40 | 是复制时页申请失败；没有证据称tar被OOM killer杀死 |
| 设备镜像静态分析 | 目标与暂存tmpfs绑定相同NUMA集合；复制采用非原子覆盖，失败返回未可靠上抛 | 能解释部署残缺却继续报告成功的机制；未完成在线映射二进制与镜像的哈希对应 |
| CPU文件失败对照 | 限制文件写入使覆盖失败、目标变短，末尾清理令整体shell返回成功 | 支持覆盖和返回码掩盖机制；不是设备ENOMEM复现或实际异常库长度测量 |

原始资料未公开，因此这些运行结果不是新环境的验收凭证；本次整理没有重跑模型或NPU实验。

## 为什么总内存有余仍会复制失败

历史设备OS初始化脚本将公共库目录及部署暂存目录的tmpfs设为`mpol=bind:32-40`，与失败时nodemask一致。该脚本来自驱动设备镜像，由设备OS启动入口加载，不是容器或vLLM启动脚本。

故障快照中，这组节点managed合计91.75GiB，各尺寸HugeTLB池合计约90.37GiB且池内空闲为零；普通Movable空闲合计仅5188KiB，分散在多个节点，部分低于水位。managed减大页池所得约1.38GiB包含已用普通页及其他用途，不能当作空闲量。节点0约818MiB空闲也不能替代绑定集合内的本次分配；普通页申请不能直接消费仍在HugeTLB池内的页。

因此必须核对设备OS的允许节点、页类别和水位，不能仅看宿主MemAvailable、总HBM余量或tmpfs的`size=4g`。该size是文件系统容量上限，不是预留物理页；部署期间暂存解包和复制目标还可能同时存在。

这些快照解释了分配路径受限和小页紧张，但没有历史逐页归属记录。不能将全部大页、池规模变化或内存压力归给某个模型，也不能认定某一`gpu_memory_utilization`值单独必然触发或存在泄漏。

## 为什么停掉模型后仍会失败

历史时序分为两个窗口：早期不同包触发公共库切换，复制期间页申请失败；先前模型随后已停止，新一轮仍比较原包哈希并跳过部署，直到目标算子使用TF库时再次失败。不能把后一个窗口描述成旧模型仍在占卡。

同机安装设备镜像的TSD静态分析显示：解包到暂存目录后，使用`cp --remove-destination -af`覆盖目标，再清理暂存目录，各阶段由分号连接。失败可留下短文件，而末尾清理成功可掩盖前序命令状态；`BasePackageWorker::DecompressPackage`还存在丢弃执行返回值并返回成功的路径。设备日志实际在复制失败窗口之后记录部署成功及包哈希，后续启动据此跳过加载。

停止模型释放资源不会自动修复设备公共目录及部署标记。此环境的不同容器也未隔离该设备公共目录；仅版本字符串相同不能替代实际包内容核对。尚无cp逐文件写audit，不能声称逐文件记录已直接证明哪一次写坏了TF库。

## 后续排查和验收顺序

1. 先保全同轮完整服务stdout、host/device plog、设备OS日志和黑匣子；按PID、设备、启动时间及内核单调时间对齐，回溯到首次部署或loader异常。较新的日志尾部正常不能排除更早的部署失败。
2. 分别核对源包、设备已部署库与缓存状态。源包若有签名封装，先确认格式再检查有效载荷；不能因普通tar工具打不开就判包损坏，也不能把某个构建的固定偏移套到所有版本。
3. 关联复制失败、NUMA/页池快照、部署结果和后续缓存命中。原进程退出后仍复现时，先查持久的设备状态，不盲目重复重启模型或增大超时。
4. 经当前任务授权后，采用匹配构建受支持的恢复机制，使设备文件与标记一致；随后依次验收原失败小用例、模型预热、服务请求路径。小用例通过不能代替完整模型验收。

更换AICPU包前核验同设备模型退出、在权重/KV占用前完成部署预检，是待验证的规避方向。长期实现应逐级传播失败，完整性检查通过后再原子切换并提交成功标记。本历史调查未执行这些修复，不提供未经该型号核实的reset、删缓存或跨版本换so命令。

## 复查条件

CANN、驱动设备镜像、TSD部署命令或错误处理、tmpfs内存策略、大页管理、包缓存规则改变时复查。只有取得异常文件原件、在线实现对应、受控恢复及目标模型验收后，才补充对应层级的闭环结论。

本案例是设备侧普通页和库部署问题，与[EPLB的Host锁页申请](eplb-full-map-pinned-host-allocation.md)、[Mooncake分层超时](mooncake-nested-timeout.md)分别取证，不能互相替代根因。
