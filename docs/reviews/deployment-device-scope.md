# 部署示例的设备范围语义

- 状态：implemented，文档及代表行为复核通过。
- 范围：workflow的服务部署reference；不改变既定容器运行方式或业务部署。

## 问题与依据

A5手工容器构造示例同时使用`--privileged`与按`NPU_IDS`追加的`--device`。示例没有说明两者组合的设备权限语义，读者可能把清单当作子集设备访问隔离，进而在没有运行时选卡约束时启动负载。

[Docker官方运行说明](https://docs.docker.com/engine/containers/run/#runtime-privilege-and-linux-capabilities)明确privileged容器可访问全部宿主设备。原有“核对可见卡范围”仍是有效门槛，但不足以解释模板中设备清单的作用。本问题有文档与公开语义证据，不声称已复现误用NPU。

## 最小修复与泛化边界

在原示例处解释权限语义，并沿用启动前已有设备范围核对：子集负载须由实际后端的选卡机制约束，核对物理/逻辑映射；需要访问隔离时使用满足要求的已验证方案。保留用户已确认的privileged分支，不把某个芯片、驱动版本的环境变量强加给所有后端，不增加脚本、依赖或资源管理系统。

| 代表条件 | 修复后的判断 |
|---|---|
| privileged容器，授权非零子集，环境入口没有选卡约束 | 设备清单不能证明隔离；落实有效运行时选卡并核对映射前，不启动NPU负载 |
| privileged容器，已授权全部设备 | 如实说明全设备访问，不增加无关子集检查；沿用既有资源协调 |
| 非privileged或托管后端，已有可验证的设备约束 | 沿用其原设备契约与映射，不套用本例、不重复分配 |
| 要求设备访问隔离，已有运行时可见卡变量 | 可见卡变量不足以证明访问隔离；使用满足该要求的已验证方案 |

## 验证边界

本轮修改仅为说明与判断门槛，检查格式、仓内引用、差异和代表请求；不以文本演练宣称真实容器设备隔离通过。单机缺库、平台条件和特定运行失败分别保留在本机证据，不扩展成所有部署的默认修复。
