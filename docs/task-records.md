# 任务材料、启动记录与运行台账

本文件维护共用的存放、命名和登记约定。workflow 建立入口，execution 执行及接手登记，runtime-snapshot 维护容器环境记录，领域执行方登记对应类型的正式测试，review 核查交付材料；各 skill 按职责引用本文件。

## 任务目录与唯一入口

- 普通事项放在 `tasks/YYYY-MM-DD/<事项名>/`，日期使用 Asia/Shanghai；每日 `索引.md` 只列事项链接。用户明确命名的长期任务放在 `tasks/<指定任务名>/`。
- 跨天继续同一事项时沿用原目录。每个事项根目录只保留 `任务说明.md` 作为状态、结论、下一步和材料入口，其他材料按需进入 `scripts/`、`configs/`、`logs/`、`results/`。
- 实验记录、验证矩阵、CI记录、交付与回顾等详细文档放在 `results/`；按实际需要创建，不为齐全增加空文档。委派材料放在 `results/assignments/<子任务编号>-用途/`，使用 `委派说明.md`、`结果.md`，同一子任务的后续结果按轮次或计划版本分段。
- 模型架构分析单独使用 `tasks/<模型名>-模型分析/<YYYYMMDD>-<分析序号>/`。同一模型的独立分析序号从 1 连续递增，新一轮在模型目录下新建同级工作目录；恢复同一次分析沿用该轮目录。每轮内部仍按材料用途分目录，模型父目录可维护简短索引。
- 已有 task_id、owner、状态和历史目录保留。本轮规则用于新建材料；历史目录迁移、文件去重或删除须有单独确认。

从 [任务模板](templates/任务说明.md) 建立入口。其他模板复制到 results 等实际位置后，调整返回任务说明及其他材料的相对链接；模板源中的同目录链接用于预览。

## 编号、用途与材料分组

- 服务编号为任务内的 `S001`、`S002` 等，每次实际启动、重启或启动重试新建一组；查看状态不新增编号。总表引用时包含任务位置，避免跨任务同号混淆。
- 三类正式测试共用编号 `TYYYYMMDD-NNN`，例如 `T20261023-001`。日期取测试开始时的北京时间，当天跨任务从三类表及既有 AISBench 表中已登记的最大流水号接续；每次实际运行独立编号，失败、中断及重跑也保留。补登记时开始时间未知则用接手登记日分配编号，并明确日期依据，不能倒填开始时间。
- 测试用途写成“硬件型号＋实际机器数及部署方式＋测试目标/对照项＋负载＋轮次”。例如“A5八机PD分离（2P6D），list基线，输入16k/输出1k，并发32，第1轮”。机器数统计参与模型服务的节点，PD 写明 P/D 分配；混合型号分别说明。只写已核实的实际情况。
- scripts/configs/logs/results 内以对应编号加简短用途分组。一次正式测试的配置、日志、结果使用同一测试编号；调参、排障及一般任务实验沿用任务内部编号，不占总表编号。

## 服务启动材料

每次启动在当前任务的 `scripts/Sxxx-用途/` 保存当次完整材料，即使内容相同也保留本次完整脚本：

```text
scripts/S002-用途/
├── start_p.sh
├── start_d.sh
└── 启动命令与差异.md
```

- PD 场景固定保留 P、D 两份完整角色文件。每份只包含本轮必需的 export 环境变量和实际 vLLM 服务命令，不加入检查、条件分支、重试、函数等防御性代码。使用本轮实际解释器和入口；需要的环境设置展开为必要 export。
- 多 P/多 D 节点仍使用这两份角色文件。rank、IP 等节点差异由说明文件中的逐节点启动命令传入；公共脚本消费这些节点值，不覆盖为另一节点的值。非 PD 场景使用一份 `start.sh`。
- `启动命令与差异.md` 保存每个节点可直接执行的完整命令、对应本地/远端文件位置，以及相较前一轮的参数和环境变量新增、删除、前后值。注明比较的服务编号；首次标记基线，无变化写一行。容器环境版本变化只补一行说明，详细环境采用容器总表中的三类记录。
- 本轮实际配置完整保存到 `configs/Sxxx-用途/`；任务说明给出本轮入口。代理等配套组件的实际节点命令写入启动说明，保持 P/D 文件只含 export 和 vLLM 命令。
- 目标服务器、容器确定后，部署前列出远端脚本的实际绝对位置供用户确认；沿用同一任务已确认的位置，不能自行另选目录。脚本准备、运行工具校验和生命周期管理由执行方在文件外完成。

## 日志采集与分析

### 已有结果汇总与补登记

仅查看、统计或补录已有测试结果时，先读取原生指标汇总和识别该轮所必需的配置、运行标识与时间信息；只保存本次使用的结果和必要配置，并记录来源。运行身份、指标单位、统计阶段及成功/总数等登记字段足够时即停止，不默认下载服务日志、plog、逐请求明细、数据集或整目录，也不为补表重新运行测试或全量盘点环境。

字段缺失或结果矛盾时，先核对已有汇总的单位、阶段与配置；仍影响结论才按需读取对应文件或记录，大明细优先在原位置有界查询或聚合。找到所需证据即停止，不能确认的字段标明缺失；从日志补取字段不等于开展故障分析，不触发完整日志备份。确需追踪异常原因或用户明确要求日志分析、完整归档时，才进入下面的诊断分支或按用户指定范围采集。

### 日志诊断

用户要求分析日志时，先把问题涉及节点、组件的完整原始日志及必要轮转文件保存到本地当前任务，再基于备份分析。PD 问题按实际涉及范围包括 P、D、proxy 等；同时收集对应节点、进程/worker 与故障时段的 plog。

```text
logs/S001-用途/20261023-160000-报错后采集/
├── P0-节点标识/
│   ├── vllm.log
│   └── plog/<原始文件名>
└── D0-节点标识/
    ├── vllm.log
    └── plog/<原始文件名>
```

- 核对实际日志配置和宿主/容器位置，保留 plog 原文件名。采集索引注明服务器、容器、原始路径、采集时间、覆盖范围和完整性；同一原件的宿主/容器路径只保存一份并注明映射。
- 正在写入的日志保留采集截止点；未找到、不可读、失败或不完整明确标注。已有完整备份仍满足本次范围时复用，否则建立新批次，保留历史。采集只读，不影响服务。
- 关联同次服务脚本、有效配置和环境版本；来源与覆盖信息集中写入任务说明的采集索引，必要时补一份批次文件清单，不为每个日志新建说明。结论定位到本地文件和行号。
- 大原件留文件，向会话只提供必要摘要；发送/上传遵守当前环境已确认的传输约束，包括适用的单次、累计或完整请求口径，不将某台机器的固定限额推广到其他机器。截断片段不能当作完整备份。

**模型精度分析例外**：ascend-model-accuracy 内部诊断、消融和回归的原生结果、大日志、plog、张量保留在该精度任务的远程位置，本机只保存分析摘要和必要的远端定位信息，不执行上述默认下载。显式要求另行下载时按用户范围处理。

### 接手手动测试

接手性能、精度或 SWE 测试时，先用已有结果、配置、运行标识、原生输出目录及时间范围辨认本次运行与用途；仅补录结果采用[已有结果分支](#已有结果汇总与补登记)，不要将“看看结果”自动转为日志诊断。查对应类型的总表和任务索引，已有同次运行就更新原行；无表项且属于正式测试时，先补登记再关联分析。调参和排障仍只记原任务，不能因接手分析就提升为正式测试。

补登记注明“手动启动”、接手/登记时间、实际开始时间或 unknown、证据来源和当前状态。缺失的命令、环境或评分保留缺口，不从另一轮拷贝。原日志和结果按真实位置引用，不为整理改名、移动正在写入的文件，也不为补字段重跑测试。测试结束后仍更新同一行，分析入口放在该行的“分析入口”列；采集范围和原件保留位置遵循本节。

## 算子开发进度与运行日志

进入算子开发、替换或验证时，沿用当前任务说明及 results 中的计划/实验记录维护阶段、实际修改、关键决策、失败、下一步和代码版本。下层若使用 `.cannbot/<算子名>/LOG.md` 等进度模板，读取其与本次任务有关的流程要求并引用本任务记录；原工具必需的状态文件仍由原工具维护。上层唯一状态仍是任务说明，不复制维护第二份整体进度，也不因模板提到子 agent 就自动委派。

每次实际编译、安装、UT、精度或性能运行建立任务内运行编号（如 `O001`），在 `logs/O001-用途/` 保留完整 stdout/stderr；命令、配置、开始/结束时间、退出码、实际代码/环境、设备、输入/reference/阈值和结果入口在同编号实验记录中关联。尚在运行或退出码不可得时如实标记，不能只留成功摘要；流水线分别保留关键步骤退出状态，不能以 tee 成功代替被测命令成功。

异常时按涉及进程、设备和时段补齐已有 plog、编译器或运行器错误文件，不默认全扫设备日志。远端完整日志先留原件，并按上面的默认采集规则备份到本任务；算子精度不自动套用模型精度的远端保留例外。大型张量、profiling 等原生数据保留真实位置和必要定位，不全量传入会话。已存在完整材料时直接引用，保留失败轮与历史，不为登记再运行。算子内部运行不进入模型三类正式测试表。

## 服务器可达性总表

本机 `records/服务器总表.md` 使用[服务器模板](templates/服务器总表.md)。它是原来源的带时间快照，不是机器注册、租约或 ready 状态的第二事实源。

先确认表的粒度和字段，再应用到本机。正式表一台宿主服务器一行，容器作为关联入口；同一宿主的多个连接入口只归并到该宿主，不凭相同 IP、相似别名或相同 NPU Name 认定宿主归属。仅确认 SSH 的端点先保留任务证据，查明宿主后再入表。展示字段为名称/别名、宿主机 IP、硬件代际、NPU 型号/卡数、整机产品型号、产品形态、宿主机 SSH 命令、已有容器及 SSH 入口、最近核验时间、备注；完整来源和探测记录留任务，不铺进主表。

容器列仅展示用户范围内已纳入的容器，不是宿主全部容器清单，也不由探测结果认定用户归属。首次整理按用户明确确认的名称等筛选条件处理，具体条件保存在本机表说明中。后续新增以实际使用为准，不要求延续首次名称筛选；须有用户确认已使用或任务记录证明确实使用过该容器，记录对应宿主、容器名称及可获得的实际ID和使用证据入口。仅发现、列举、查询状态或符合原名称筛选不算使用，不自动补入。容器重建或ID变化须重新核对，不能沿用同名旧容器的使用证据。未纳入项留必要任务证据，不逐项铺入服务器表；没有符合条件的项写“无已纳入容器记录”，不能据此声称宿主没有容器。

IPv4 默认按前三段分展示区，分区和区内 IP 按数值升序；新增插入原分区，其他已确认的展示规则优先。这不是对真实网段掩码的认定。IPv6、域名及未确认地址单列，不伪造分区。

硬件代际、芯片型号、整机产品型号和产品形态不是同一字段。按当前厂商资料及实际设备/资产证据核对，可参考[官方产品形态说明](https://www.hiascend.com/document/detail/zh/Glossary/productform/hardwaredesc_0001.html)、[服务器规格](https://www.hiascend.com/hardware/ai-server)及[超节点产品](https://www.hiascend.com/hardware/cluster)；例如 Atlas 650E 服务器、Atlas 850E 风冷超节点和 Atlas 950 SuperPoD 液冷超节点是不同整机产品/形态，不能仅凭“A5”或 NPU Name 判断。其他代际同样按其实际产品资料核对，未查明的不套用旧代际映射。Pod 成员注明所属系统，卡数记录本宿主实际范围，不能用整套 Pod 的规模或容器可见设备数代替物理卡数。

- 首次建立或用户要求刷新时，汇总全部已保存的具体 SSH 目标（含 Include、应用会话和可还原的 known_hosts 记录）以及原管理工具已登记目标；不能还原真实地址的哈希 known_hosts 只记覆盖缺口，不猜测或扫描。通配 Host 不是一台服务器。按实际 host/port/user 去重，保留别名、跳板及来源引用。
- 优先使用原工具的只读清单能力；旧 VAWS inventory 只覆盖其登记目标，不能代管新 MindIE 状态。新来源无枚举入口或不可读时列明覆盖缺口，不创建会话/运行来凑清单。来源与具体操作见 [init 约定](../.agents/skills/ascend-workbench-init/references/operations.md#保存目标与-npu-接入)。
- “SSH 可达”须有本次实际认证登录并成功执行只读命令的证据；TCP 连通、旧登记或上次成功不能替代。分别记录连接失败、待认证/host-key 未核验、未探测、SSH 成功但硬件未知、确认有/无 NPU。失败、待接入及宿主未核验端点留任务证据；当前可达且宿主已核验的服务器进入主表，硬件细项未知时标缺口。
- 连接与硬件采集采用有界只读检查；不读取私钥内容、解密密码或修改认证，不绕过 host-key 校验。可用硬件信息只取实际工具/命令证据，不能从别名、镜像或旧记录推断型号；SSH/NPU 成功也不等于设备空闲或可租用。
- 记录检查时间和证据入口。任务实际使用目标时更新该目标，要求完整刷新时才检查全表；无新检查不刷新时间。表内不保存密码、令牌或私钥，真实接入与资源归属仍由原工具管理，不自动部署或改变服务。

## 容器总表与最小环境记录

实际总表固定在工作台根的 `records/容器总表.md`，由 [容器总表模板](templates/容器总表.md) 建立。records 为本机忽略目录；首次实际使用、新建或修改容器时逐步登记，不自动盘点历史所有容器。它是复现与查找记录，资源归属和生命周期仍由原工具管理。

服务器、容器名/实际 ID、稳定容器编号及环境版本用于定位。相同容器更名仍保留编号，同名重建的实际容器使用新编号。镜像、代码或依赖变化时新增环境版本，保留旧版本；测试固定关联当时版本。常规复现材料只记录三类：

| 内容 | 必需记录 |
|---|---|
| 原始镜像 | 文件位置/文件名；直接拉取则记录地址和实际镜像 ID/digest |
| 叠加 PR | 仓库、顺序、PR、实际采用的来源提交及叠加后提交；提交细节以 Git 历史为准 |
| 替换依赖 | 只记录改动项的名称、前后版本或产物、获取位置 |

不默认生成环境准备脚本、全量包清单或长篇复现文档。独立环境诊断按具体问题补最少字段，未知项如实标明。

SSH 入口记录对外地址、端口、用户名和认证方式。按用户已确认的本机管理方式，明文密码只写入此容器总表；更新 SSH 配置后同步相应表项。口令不复制到聊天、任务报告、启动脚本、命令参数或日志，也不进入 Git、公开模板或审视材料。尚未掌握的密码标明未掌握，不猜测。SSH 配置和登录验证细节保留在所属任务。

## PR 顺序叠加

在本次已授权的实际业务 repo/worktree 中核对基线和 dirty 内容，保护已有工作。按确认的 PR 顺序逐个处理：固定来源及提交范围，用 cherry-pick -x 保留 PR 内原始提交顺序、作者和来源，记录该 PR 叠加前后 SHA，再继续下一个。一个 PR 可包含多个原始提交，不把多个 PR 改写成一份手工源码补丁。

PR 已包含在基线、依赖不满足或无法直接叠加时明确记录状态，不冒充新叠加成功。冲突解决单独呈现解决 diff 并记录归属；本地额外修改单独留提交/差异，不伪称原 PR 内容。Git 作者、DCO 和提交/推送审核继续遵循根规则，PR 描述仅按用户明确要求修改。

## 三类正式测试总表

分别维护 [性能测试表](templates/性能测试总表.md)、[精度测试表](templates/精度测试总表.md)、[SWE 测试表](templates/SWE测试总表.md)，本机位置分别为 `records/性能测试总表.md`、`records/精度测试总表.md`、`records/SWE测试总表.md`。按本轮实际评测目标选择表，AISBench 是工具而非测试类型。SWE 指软件工程数据集上的 agent 评测，不是 skill 演练；若一项任务有独立的三种运行，分别登记，不能把性能指标填进精度或 SWE 列。

- 只登记正式测试，包括明确要求的正式基线、评测和最终验收。调参摸底、候选筛选、排障复现、精度内部诊断/消融及内部回归留各自任务；使用 AISBench 或接手手动日志不会改变此边界。
- 每次正式运行独立一行，失败、中断及重跑也保留；同配置多轮逐轮记录，再按需汇总。共用字段包括编号、真实时间、用途、发起方式/接手时间、当时环境、完整实际命令和配置、状态、原生结果及分析入口。按本任务同编号分组保存材料；表中直接填写结果和单位，不能只给文件链接。
- 性能表固定指标：TTFT 平均值/P90（ms）、输入/输出吞吐（token/s）、成功/总请求数。缺失或不适用如实标记，不填零、不用其他百分位替代 P90；TPOT 或每卡吞吐按任务补充。
- 精度表明确模型/配置、数据集版本及 split、评测器、官方指标名称/值/单位、实际评测样本数及执行失败数。执行失败和答错分别表述；内部异常率不能冒充官方评分。
- SWE 表明确数据集/版本/split、agent/模型及配置、代码基线、runner/评测器、原生指标名称/值/单位、总实例数、已评测数、解决数和执行错误数。按原评测器定义记录 outcome 和分母；未提供的字段写缺失或不适用，不默认使用 pass@1，也不把模型问答精度当作 SWE 解决率。
- 测试时状态记录当时容器/服务的观察时间、就绪、重启/预热及运行异常或变更，不用后来的状态覆盖历史。多机 P/D 及请求端分别关联当时版本和完整启动材料；无服务或容器的 SWE runner 明确不适用。
- 写入前读取三类表及必要的旧表索引，保留其他任务条目。既有 `records/AISBench测试总表.md` 原样保留供历史查询和编号去重，不在本轮批量迁移、删除或重新编号；历史补录与拆分另按用户范围处理。

## 交付检查

review 按任务涉及范围核对材料可读、编号对应和入口有效；核对日志/plog 的范围与完整性，并遵循精度分析的远端保留例外；核对本次完整脚本、节点命令及差异说明；核对容器/测试登记与实际环境、配置、结果一致。结果简记在任务说明，缺项明确列出，不新增一套检查报告，也不因记录齐全声称真实运行或复现成功。
