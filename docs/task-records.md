# 任务材料、启动记录与运行台账

本文件维护共用的存放、命名和登记约定。workflow 建立入口，execution 执行，runtime-snapshot 维护容器环境记录，benchmark 登记正式测试，review 核查交付材料；各 skill 按职责引用本文件。

## 任务目录与唯一入口

- 普通事项放在 `tasks/YYYY-MM-DD/<事项名>/`，日期使用 Asia/Shanghai；每日 `索引.md` 只列事项链接。用户明确命名的长期任务放在 `tasks/<指定任务名>/`。
- 跨天继续同一事项时沿用原目录。每个事项根目录只保留 `任务说明.md` 作为状态、结论、下一步和材料入口，其他材料按需进入 `scripts/`、`configs/`、`logs/`、`results/`。
- 实验记录、验证矩阵、CI记录、交付与回顾等详细文档放在 `results/`；按实际需要创建，不为齐全增加空文档。委派材料放在 `results/assignments/<子任务编号>-用途/`，使用 `委派说明.md`、`结果.md`，同一子任务的后续结果按轮次或计划版本分段。
- 模型架构分析单独使用 `tasks/<模型名>-模型分析/<YYYYMMDD>-<分析序号>/`。同一模型的独立分析序号从 1 连续递增，新一轮在模型目录下新建同级工作目录；恢复同一次分析沿用该轮目录。每轮内部仍按材料用途分目录，模型父目录可维护简短索引。
- 已有 task_id、owner、状态和历史目录保留。本轮规则用于新建材料；历史目录迁移、文件去重或删除须有单独确认。

从 [任务模板](templates/任务说明.md) 建立入口。其他模板复制到 results 等实际位置后，调整返回任务说明及其他材料的相对链接；模板源中的同目录链接用于预览。

## 编号、用途与材料分组

- 服务编号为任务内的 `S001`、`S002` 等，每次实际启动、重启或启动重试新建一组；查看状态不新增编号。总表引用时包含任务位置，避免跨任务同号混淆。
- 登记的 AISBench 测试编号为 `TYYYYMMDD-NNN`，例如 `T20261023-001`。日期取测试开始时的北京时间，当天跨任务从测试总表接续流水号；每次实际运行独立编号，失败、中断及重跑也保留。
- 测试用途写成“硬件型号＋实际机器数及部署方式＋测试目标/对照项＋负载＋轮次”。例如“A5八机PD分离（2P6D），list基线，输入16k/输出1k，并发32，第1轮”。机器数统计参与模型服务的节点，PD 写明 P/D 分配；混合型号分别说明。只写已核实的实际情况。
- scripts/configs/logs/results 内以对应编号加简短用途分组。一次测试的配置、日志、结果使用同一测试编号；一般任务实验沿用任务内部编号，不占 AISBench 总表编号。

## 服务启动材料

每次启动在当前任务的 `scripts/Sxxx-用途/` 保存当次完整材料，即使内容相同也保留本次完整脚本：

```text
scripts/S002-用途/
├── start_p.sh
├── start_d.sh
└── 启动命令与差异.md
```

- PD 场景固定保留 P、D 两份完整角色文件。每份只包含本轮必需的 export 环境变量和实际 vLLM 服务命令，不加入检查、条件分支、重试、函数等防御性代码。使用本轮实际解释器和入口；需要的环境设置展开为必要 export。
- 多 P/多 D 节点仍使用这两份角色文件。rank、IP 等节点差异由说明文件中的逐节点启动命令传入；公共脚本消费这些节点值，不覆盖为另一节点的值。非 PD 场景使用一份 `start.sh`。
- `启动命令与差异.md` 保存每个节点可直接执行的完整命令、对应本地/远端文件位置，以及相较前一轮的参数和环境变量新增、删除、前后值。注明比较的服务编号；首次标记基线，无变化写一行。容器环境版本变化只补一行说明，详细环境采用容器总表中的三类记录。
- 本轮实际配置完整保存到 `configs/Sxxx-用途/`；任务说明给出本轮入口。代理等配套组件的实际节点命令写入启动说明，保持 P/D 文件只含 export 和 vLLM 命令。
- 目标服务器、容器确定后，部署前列出远端脚本的实际绝对位置供用户确认；沿用同一任务已确认的位置，不能自行另选目录。脚本准备、运行工具校验和生命周期管理由执行方在文件外完成。

## 日志采集与分析

用户要求分析日志时，先把问题涉及节点、组件的完整原始日志及必要轮转文件保存到本地当前任务，再基于备份分析。PD 问题按实际涉及范围包括 P、D、proxy 等；同时收集对应节点、进程/worker 与故障时段的 plog。

```text
logs/S001-用途/20261023-160000-报错后采集/
├── P0-节点标识/
│   ├── vllm.log
│   └── plog/<原始文件名>
└── D0-节点标识/
    ├── vllm.log
    └── plog/<原始文件名>
```

- 核对实际日志配置和宿主/容器位置，保留 plog 原文件名。采集索引注明服务器、容器、原始路径、采集时间、覆盖范围和完整性；同一原件的宿主/容器路径只保存一份并注明映射。
- 正在写入的日志保留采集截止点；未找到、不可读、失败或不完整明确标注。已有完整备份仍满足本次范围时复用，否则建立新批次，保留历史。采集只读，不影响服务。
- 关联同次服务脚本、有效配置和环境版本；来源与覆盖信息集中写入任务说明的采集索引，必要时补一份批次文件清单，不为每个日志新建说明。结论定位到本地文件和行号。
- 大原件留文件，向会话只提供必要摘要，遵守用户每个发送/上传载荷小于 1MB 的限制；截断片段不能当作完整备份。

**模型精度分析例外**：ascend-model-accuracy 内部诊断、消融和回归的原生结果、大日志、plog、张量保留在该精度任务的远程位置，本机只保存分析摘要和必要的远端定位信息，不执行上述默认下载。显式要求另行下载时按用户范围处理。

## 容器总表与最小环境记录

实际总表固定在工作台根的 `records/容器总表.md`，由 [容器总表模板](templates/容器总表.md) 建立。records 为本机忽略目录；首次实际使用、新建或修改容器时逐步登记，不自动盘点历史所有容器。它是复现与查找记录，资源归属和生命周期仍由原工具管理。

服务器、容器名/实际 ID、稳定容器编号及环境版本用于定位。相同容器更名仍保留编号，同名重建的实际容器使用新编号。镜像、代码或依赖变化时新增环境版本，保留旧版本；测试固定关联当时版本。常规复现材料只记录三类：

| 内容 | 必需记录 |
|---|---|
| 原始镜像 | 文件位置/文件名；直接拉取则记录地址和实际镜像 ID/digest |
| 叠加 PR | 仓库、顺序、PR、实际采用的来源提交及叠加后提交；提交细节以 Git 历史为准 |
| 替换依赖 | 只记录改动项的名称、前后版本或产物、获取位置 |

不默认生成环境准备脚本、全量包清单或长篇复现文档。独立环境诊断按具体问题补最少字段，未知项如实标明。

SSH 入口记录对外地址、端口、用户名和认证方式。按用户已确认的本机管理方式，明文密码只写入此容器总表；更新 SSH 配置后同步相应表项。口令不复制到聊天、任务报告、启动脚本、命令参数或日志，也不进入 Git、公开模板或审视材料。尚未掌握的密码标明未掌握，不猜测。SSH 配置和登录验证细节保留在所属任务。

## PR 顺序叠加

在本次已授权的实际业务 repo/worktree 中核对基线和 dirty 内容，保护已有工作。按确认的 PR 顺序逐个处理：固定来源及提交范围，用 cherry-pick -x 保留 PR 内原始提交顺序、作者和来源，记录该 PR 叠加前后 SHA，再继续下一个。一个 PR 可包含多个原始提交，不把多个 PR 改写成一份手工源码补丁。

PR 已包含在基线、依赖不满足或无法直接叠加时明确记录状态，不冒充新叠加成功。冲突解决单独呈现解决 diff 并记录归属；本地额外修改单独留提交/差异，不伪称原 PR 内容。Git 作者、DCO 和提交/推送审核继续遵循根规则，PR 描述仅按用户明确要求修改。

## AISBench 总表

实际总表固定在 `records/AISBench测试总表.md`，由 [测试总表模板](templates/AISBench测试总表.md) 建立。写入前读取最新内容，保留其他任务已登记项。

- 登记用户明确要求的 AISBench 测试、正式基线和最终验收。调优 skill 的内部摸底/候选筛选留在调优任务；模型精度 skill 内部诊断测试即使用到 AISBench，也由精度任务独立管理，不登记总表。
- 每次登记的实际测试独立一行，包括失败和中断；同配置多轮逐轮记录，再按需汇总。保存完整实际命令、配置、工具/数据来源和原生结果，分别放到本任务同编号的 configs/logs/results 分组。
- 列顺序为“测试编号、时间、用途、关键结果、容器及环境版本、服务启动材料、AISBench命令与配置、测试时状态、原生结果位置”。复现信息位于关键结果之后，不把结果列写成单纯文件链接。
- 性能关键结果直接写 TTFT 平均值、TTFT P90、输入吞吐、输出吞吐，并注明单位及成功/总请求数。TTFT 统一毫秒，吞吐注明 token/s；从本轮原生统计或可用的逐请求数据取得，缺失或未完成如实标记。每卡吞吐和 TPOT 不作为总表固定指标，任务另有要求时补充。
- 用户明确要求的正式精度评测展示官方评分、样本数、失败数；这里不包含精度诊断 skill 的内部实验。不适用或未产生的指标写明，不填零，不用其他百分位替代 P90。
- 测试时状态记录本轮容器/服务观察时间、就绪、重启/预热及测试中异常或变更；不用后来更新的状态覆盖历史。多机 P/D 及请求端实际使用的容器分别关联当时版本，服务启动材料指向该轮完整文件。

## 交付检查

review 按任务涉及范围核对材料可读、编号对应和入口有效；核对日志/plog 的范围与完整性，并遵循精度分析的远端保留例外；核对本次完整脚本、节点命令及差异说明；核对容器/测试登记与实际环境、配置、结果一致。结果简记在任务说明，缺项明确列出，不新增一套检查报告，也不因记录齐全声称真实运行或复现成功。
