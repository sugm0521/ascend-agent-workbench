# 每日任务归档、知识维护与授权发布

## 已确认的安排

用户于2026-10-15确认：北京时间每周一至周五09:00独立执行，知识库存放于`knowledge/`；除每日记录与知识外，也自动推送有明确授权且已完成验证的代码和skill改动。每次实际推送后提供详细反馈。该持续授权仅适用于下述范围，可由用户后续修改或取消。

使用Codex项目独立定时任务；调度配置由应用管理，不手写系统cron或自动化配置文件。任务需要本机文件，执行时电脑须开机、应用须运行。工作台实际Git根由根规则确认，所有Git操作指定该根。

## 先检索、再归档

1. 核对根规则、当前分支/HEAD、暂存和未暂存内容、远端、任务owner与当前时间。记录本次读取截止时间，之后发生的新修改交下一轮处理。
2. 从上次成功回执的`coverage_end`开始查找变化；缺少回执时先检查近两日任务说明、交付索引和Git变更，明确首轮覆盖范围，不宣称已回填全部历史。周一或停机恢复后覆盖上次成功截止以来的变化，包括周末记录。任务未落盘或证据不可读时记录缺口，不从聊天标题猜测结果。
3. 先读小型任务说明与交付/验证摘要，按task_id去重；只在核实具体结论时读取必要日志片段、源码或官方来源。活动任务保持原owner和状态，不为归档抢占、重跑、停止服务或占用设备。
4. 更新`knowledge/daily/YYYY-MM-DD.md`，日期采用本次北京时间执行日期。同日重跑更新同一文件，保留覆盖区间与重要修正，不重复创建同一条目。记录逐任务目标、实际处理、结果、证据层级、限制、待办与发布情况；日报是有日期的快照，任务说明仍是状态权威。

日报只保存有恢复价值的信息。原始对话、海量日志、权重/镜像、内部地址/凭据、本机配置和临时环境状态不复制到公共仓；必要证据可记录相对位置、哈希、时间及是否仅本机可访问，不能给出伪装为仓内可访问的链接。

## 知识归纳

按[知识库约定](../knowledge/README.md)检索已有条目与相关任务证据，再决定新增、更新、合并或暂不收录。一般任务进日报；有复用价值且具备证据的推理、故障判断和边界才进入知识条目。

新知识与来源矛盾、结论未定或版本条件不明时保留candidate状态和缺口；不能把假设、规避、中断评测或静态检查升格为已修复/正式验收。过期条目按历史保留规则处理，不因一次检索未命中就宣布过期。默认从本地任务和固定版本源码取证，仅在确有缺口时检索外部主来源，不每天全网抓取。

每日调用独立的[ascend-knowledge-curation](../.agents/skills/ascend-knowledge-curation/SKILL.md)。过期、合并或替代前保存完整旧条目到`knowledge/history/`，记录具体过期原因、触发证据和替代关系，当前入口保留指向历史的说明；不直接删除。知识只在`knowledge/`维护，不自动改写skill、外部依赖或Codex长期记忆。

## 检查遗漏并推送

每日检查所有工作台tracked差异、未跟踪的维护文件以及尚未推送的提交，不能只检查刚生成的日报。按下面三类逐项说明处理结果：

| 内容 | 自动处理条件 |
|---|---|
| 日报、知识、必要任务摘要、已核实的发布状态修正 | 本轮产生或已核实，来源/范围清楚，检查通过后可提交推送 |
| 代码、skill、配置示例及依赖登记 | 找到明确的用户实施/发布授权与具体范围，任务已经完成、适用验证通过，文件内容属于该范围且无其他会话继续写入，才可提交推送 |
| 授权不明、进行中、验证缺失、候选方案和本机产物 | 保留原文件与暂存状态，报告具体位置、原因和恢复条件；不自动扩大授权或补做业务实验 |

本持续授权允许发布已获用户授权实施并已完成验证的维护改动，不意味着每天可自行实现新功能、升级依赖或实施skill候选。业务Git仓库和`deps/`不纳入工作台自动发布范围；业务仓已有具体发布授权的事项仍按该仓规则独立处理，不混进工作台提交。GitHub PR修改遵循原审核要求，不自动改PR描述。

发布遵循以下顺序：

1. 列出逐文件/hunk白名单、对应任务/授权与验证；核对本地领先远端的每个提交，防止直接push夹带其他未授权提交。
2. 使用独立索引或等效隔离准备，保留不属于本轮的dirty/staged内容。发布前再核对文件哈希与owner；内容变化时重新审查，不覆盖活动文件。禁止`git add .`、覆盖式reset、clean、强推或为了同步自动stash全部工作。
3. 运行与改动匹配的检查。文档查来源/链接/状态，skill查格式和代表行为，脚本查必要功能；已有有效证据可在固定内容/条件一致时复用，不为归档重跑NPU实验。
4. 核对GitHub和真实Git凭据均为`<account>`、目标仓库/分支与作者信息，提交包含匹配DCO。对本次outgoing提交估算上传对象包，完整新增对象的保守包也必须小于1,000,000字节；超限则缩小范围并说明，不把大包拆成多次来绕过本轮限制。
5. 普通推送到工作台`origin/main`。远端推进时重新核对差异；有冲突或授权范围变化则保留候选并报告，不强推。推送后回读远端SHA，并检查已发布文件、暂存区及保留内容。
6. 回执保存到忽略目录`.workbench-local/daily-sync/`，至少包含覆盖起止、实际提交/远端SHA、文件白名单、检查、保留项与包大小。仅在归档完整落盘且发布回读成功后推进成功截止点；失败保留上次成功位置供重试。无变化的成功检查可推进截止点，不制造空提交。

不创建第二套服务器、会话或资源状态。回执仅记录这项归档发布工作的进度；调度仍由原应用管理。

## 每次推送后的详细反馈

反馈必须在每轮独立运行结果中完整呈现，不能只写“已同步”或只给日报链接。按实际改动多少决定长度，至少包括：

- **提交与覆盖**：执行/覆盖时间、分支、各提交链接和远端回读结果。
- **逐事项实际变化**：每个任务做了什么、解决什么问题、结果和限制；不能只列任务名或文件数。
- **知识变化**：新增/更新/合并的条目路径、具体可复用结论、适用版本/条件、证据与仍未确认部分；无值得沉淀的知识时直说原因。
- **维护文件变化**：完整文件清单按事项归组，说明行为或规则的前后差异，不贴完整原始文件。
- **验证**：实际检查和结果，分开静态、离线、真实运行；未跑/失败保留可见。
- **保留项**：哪些源码、skill、候选和任务内容没有推送、各自原因及下一步；确认本机详细资料与原暂存内容得到保留。
- **发布核对**：作者/DCO、上传包大小、远端SHA，以及需要用户处理的事项。

没有新变化、没有新失败或待处理事项时不打扰用户。有实际推送、重要知识修正、失败或需要人工处理时反馈。网络、认证或调度失败不能写成已同步。
