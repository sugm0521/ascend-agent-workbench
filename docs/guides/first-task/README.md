# 无服务器入门：分析 vLLM-Ascend 启动材料

本案例模拟“请求的最大上下文长度超过当前 KV Cache 可容纳的 token 数，服务启动失败”。用于体验业务材料分析、证据定位和下一步建议；阅读即可完成，不要求业务仓、私有知识库、Python、vLLM、服务器或 NPU。

所有参数和日志均为教学合成材料，不是实际 vLLM-Ascend 版本的原生日志、真实模型配置或运行验收。日志采用简化字段以表达约束，不用于匹配某一版本的真实报错格式。

## 输入材料与问题

- [启动参数摘录](launch-parameters.json)：请求的 max_model_len 为 16384，示例 gpu_memory_utilization 为 0.80。
- [合成启动日志](synthetic-startup.txt)：本案例明确假定，在记录的配置下单个请求的 KV Cache 容量上限为 8192 token；随后长度校验失败。

用户希望服务启动，但不知道应该改什么。源码、真实模型规格、芯片数量、可用显存、并行与缓存配置和实际版本均未提供；这些缺口不能由示例值补造。

## 预期交付与判断边界

| 应交付内容 | 核对要点 |
|---|---|
| 直接原因 | 对应参数和日志行，说明示例请求长度 16384 超过给定容量 8192，校验没有通过 |
| 最小调整候选 | 若业务可以缩短上下文，可建议将 max_model_len 调到给定容量范围内，例如 8192 或更低；需要确认业务要求和目标版本实际限制，不能宣称调整后必然启动成功 |
| 保留长上下文的路径 | 若业务必须使用 16384，先核对真实版本、模型/缓存布局、并行配置和可用内存，再判断如何增加容量；不直接保证提高 gpu_memory_utilization 或增加卡数就能解决 |
| 尚未证明的结论 | 材料不足以定位为何容量是 8192，也不能证明硬件总内存不足、实现存在 bug，或服务不存在其他启动问题 |
| 真实环境验证方法 | 在获授权的目标环境核对实际生效参数及同一次启动的容量/错误，保留退出状态和后续启动证据；启动后再按目标上下文做请求验收，不以错误消失替代完成 |

只读分析可以完成本案例。案例没有可执行的模拟推理服务，也不要求为了学习启动模型。若用户另行提供真实材料，转入对应任务、核对目标版本及适用规则，不直接套用本案例结论。
